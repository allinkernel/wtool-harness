# 01 架构与原理

## 起因：旧做法为什么会痛

我最早的做法（`~/source/mytool`，还在）是：

```
仓库里的 install_all.sh  →  递归调用各子项目的 wsw_install.sh  →  把文件复制/安装到 $HOME
```

问题出在"复制"：

| 痛点 | 具体表现 |
|---|---|
| **两份真相** | 我用着用着顺手改了家目录里的那份，仓库那份就过期了；下次同步又覆盖回来 |
| **不知道改了什么** | `~/.zshrc` 里东一行西一行，几个月后完全不记得哪行是哪个工具加的 |
| **撤不干净** | 想卸载某个工具，只能凭记忆找它加过什么 |
| **换机器要重来** | 每台机器复制一遍，然后各自漂移 |

新设计的答案：**不做安装，只做链接和注入。**

---

## 三层结构

```
┌─ 引擎（全机器唯一一份）────────────────────────────────┐
│  bootstrap/                                            │
│    wtool.sh          CLI：install / provision / …      │
│    lib/wtool_plan.py 规划器：算"要做什么"（只写临时目录）│
│    lib/wtool_fs.sh   执行器：真正动文件系统            │
│    lib/wtool_os.sh   探测 OS / 架构 / 并行度           │
│    templates/stub.sh 项目存根模板                      │
└────────────────────────────────────────────────────────┘
              ↓ 读声明                    ↓ 写状态
┌─ 项目（每个仓库一份）──────┐   ┌─ 状态（每台机器一份）──────┐
│  <项目>/wtool.xml  声明     │   │  ~/.local/state/wtool/     │
│  env.zsh / env.bash  被注入 │   │    registry.tsv  谁占了哪  │
│  install.sh 存根            │   │    <id>/journal.tsv 做过啥 │
│  uninstall.sh 存根          │   │    <id>/meta.tsv  装的是啥 │
└─────────────────────────────┘   └────────────────────────────┘
```

**关键分工**：
- 项目只**声明**（要链什么、要注入什么），不含逻辑 → 加新工具不用改引擎
- 引擎唯一 → 行为一致、可测试、可演进
- 状态独立 → 卸载依据是"我实际做过什么"，而不是"重新推导一遍"

## 一次 `install` 发生了什么

以 `terminal/tmux` 为例：

```
wtool install terminal/tmux
  │
  ├─① 检查：是 git 仓吗？工作区干净吗？（这样才知道装的是哪个版本）
  │
  ├─② 规划器（Python）读取
  │     terminal/tmux/wtool.xml
  │     + 当前的 ~/.zshrc 内容
  │     + 状态目录里的 registry（看有没有别人占了同一个路径）
  │   → 算出"要做哪些事"和"~/.zshrc 应该变成什么样"
  │   → 输出到临时目录，不碰任何真实文件
  │
  ├─③ 执行器（Shell）照着做：
  │     建软链 ~/.wtool/links/terminal/tmux     → 项目真实目录
  │     建软链 ~/.tmux.conf                     → 上面那个链接下的 tmux.conf
  │     写 ~/.zshrc（在原内容末尾按优先级插入受管块）
  │
  └─④ 记账：把做过的每一件事写进 journal.tsv
          （建了哪个软链、写了哪个文件、块的内容哈希）
```

**为什么规划用 Python、执行用 Shell**：
Python 擅长文本处理（解析 XML、算 rc 文件的新内容、排序插入），
但不该碰文件系统（不好测、容易写出两套逻辑）；
Shell 擅长落盘（`ln -s` / `mv` / 原子替换），但写复杂文本逻辑很痛苦。
所以：**Python 只算不写（除临时目录），Shell 只写不算。**

## 稳定地址：`~/.wtool/links/<项目id>`

这是整套设计里最重要的一环。

```
~/.tmux.conf
  → ~/.wtool/links/terminal/tmux/tmux.conf     ← 中转（引擎自动建）
      → ~/self/wtool/terminal/tmux/tmux.conf   ← 仓库真实文件
```

**为什么绕一层**：

| 好处 | 说明 |
|---|---|
| 仓库可搬家 | `~/self/wtool` 换成 `~/src/wtool`，只要重跑 install 重建中转链，配置文件一个字不改 |
| 配置内部好引用 | 项目里的配置要引用同项目的其它文件时，写 `$HOME/.wtool/links/<id>/bin/xxx`，跨机器通用 |
| 卸载有据可依 | journal 里记的就是这条链，删的时候能确认"它还是我建的那条吗" |

> 代价：`<id>` 成了对外契约（出现在链接路径、rc 块标记、配置引用里），**改了 id 必须重装**。

## 受管块：往 `~/.zshrc` 里写什么

```sh
# >>> wtool:terminal/tmux schema=1 engine=1.0.0 prio=50 head=951e888 manifest=f9cc863291b5 >>>
WTOOL_PROJECT_ID='terminal/tmux'
WTOOL_PROJECT_DIR="$HOME/.wtool/links/terminal/tmux"
export WTOOL_PROJECT_ID WTOOL_PROJECT_DIR
WTOOL_PROJECT_ROOT=$(readlink -f -- "$WTOOL_PROJECT_DIR" 2>/dev/null || printf '%s' "$WTOOL_PROJECT_DIR")
export WTOOL_PROJECT_ROOT
[ -r "$WTOOL_PROJECT_DIR/env.zsh" ] && . "$WTOOL_PROJECT_DIR/env.zsh"
# <<< wtool:terminal/tmux <<<
```

几个刻意的设计：

| 设计 | 为什么 |
|---|---|
| 开头结尾有 `# >>>` / `# <<<` 标记 | 能精确删除，不碰你其它内容 |
| `[ -r ... ] &&` 守卫 | 仓库被删/搬家后，shell 不报错，静默跳过 |
| 块里**没有时间戳** | 有时间戳的话，每次重装块内容都变 → 就不幂等了 |
| `head=` / `manifest=` | 记录装的是哪个版本（只用于溯源和提示） |
| `prio=` | 决定块之间的顺序，和安装先后无关（按 `(prio, id)` 排） |

`WTOOL_PROJECT_*` 这三个变量**只在 source 期间有效**（多个项目的块会依次覆盖），
所以 `env.zsh` 里应该立刻把它们拷进自己的变量，例如：

```zsh
export WTOOL_TMUX_DIR="$WTOOL_PROJECT_DIR"
```

## `install` 与 `provision` 的边界

```
wtool provision <项目>          ← 不可逆的一层
  ├─ 阶段 1  <system-file>   换系统配置文件（备份/还原，进 journal）
  ├─ 阶段 2  <source>        拉上游源码、固定版本、建 wsw 分支、铺 overlay
  └─ 阶段 3  <provision>     跑 ansible / shell 任务（装包、编译）

wtool install <项目>            ← 可逆的一层
  └─ 软链 + rc 块

wtool bootstrap                 ← 一条命令：按优先级对每个项目依次做上面两件事
```

**为什么 apt 和编译不算"可逆"**：它们本来就不需要回退——apt 包 `apt-get remove` 就行，
编译产物统一装到 `~/.wtool/usr`，删掉即可。把它们塞进 `install` 的 journal 只会
让"完全配对"这条不变量变成谎言。

**但 `<system-file>` 是可逆的**（它只是文件，备份+还原），所以它进 journal，
`wtool uninstall` 会把 `/etc/apt/sources.list.d/ubuntu.sources` 还原成原样。

## 状态目录：撤销的唯一依据

```
~/.local/state/wtool/
├── registry.tsv               所有登记的路径 → 属于哪个项目（用来发现跨项目冲突）
├── created-rc.tsv             哪些 rc 文件是 wtool 创建的（卸载时该删就删）
└── <项目id>/
    ├── journal.tsv            做过的每一件事（卸载时逆序重放）
    ├── meta.tsv               版本、时间、来源
    ├── provision.log           provision 任务的执行记录
    └── provisioned/<marker>   幂等标记（装过就不再装）
```

**为什么卸载靠 journal 而不是"重新推导"**：
你装了 v1 版本的清单，之后清单改成了 v2，这时卸载——
如果重新推导，算出来的是 v2 的逆操作，跟实际装过的东西对不上。
journal 记的是"我实际做过什么"，所以永远对得上。

## 关键取舍一览

| 选择 | 好处 | 代价 |
|---|---|---|
| 引擎唯一（bootstrap 一份） | 行为一致、可测、改一处全生效 | 项目不能脱离 bootstrap 独立安装（存根会提示怎么装） |
| 项目只放声明 | 加工具不用碰引擎 | 逻辑能力有限（复杂需求要写脚本，走 provision） |
| Python 只算不写 / Shell 只写不算 | 可单测 + 落盘逻辑唯一 | 两个文件、一次临时目录往返 |
| 绕一层中转链接 | 仓库可搬家、配置跨机器通用 | `<id>` 成为契约；`readlink` 多一跳 |
| 块里不放时间戳 | 幂等 | 溯源信息得去 `meta.tsv` 看 |
| 卸载靠 journal | 精确、可审计 | 状态目录丢了就没法自动卸载（得手工清） |

## 已验证的行为（测试就是证据）

```sh
cd ~/self/wtool/bootstrap
./tests/run_all.sh          # pairing 27/27 + provision 24/24
```

| 测试 | 验证什么 |
|---|---|
| `tests/pairing_test.sh` | install→uninstall 字节级还原；重复装不变化；安装顺序无关；脏仓库拒绝；dry-run 无副作用；仓库搬家 |
| `tests/provision_test.sh` | 换源三种模式 + 备份还原；按发行版自动生成源；源码同步与幂等；任务 marker；when 过滤 |
| `tests/e2e_repo_sync_test.sh` | 真实走一遍 repo init → repo sync → install → uninstall |
| `tests/container_test.sh` | 干净 ubuntu:24.04 容器里端到端（需 docker） |

> ⚠️ 跑 `e2e_repo_sync_test.sh` 时它会在 `/tmp` 建工作目录——
> **绝不要把测试目录放在任何 repo 工作区内部**，原因见 `06-排错.md`。
